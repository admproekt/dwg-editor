# План: проекты-репозитории, навыки и каталог

Статус: проект решения, до согласования ничего не реализовано. Основа: гайд Uniify «От референса и чертежей до 3D и видео» (23 стр.), опыт работы над проектом «Сириус» и текущее устройство плагинов `dwg-editor` и `3d-editor`.

## 1. Что берём из гайда

В гайде нет кода, но у него есть схема работы, которую стоит повторить.

| Приём гайда | Как проявляется | Что делаем у нас |
| --- | --- | --- |
| Проект — единица работы | Всё лежит в одном проекте, его можно сохранить и открыть заново («Save», «Open from cloud») | Проект — папка с git-репозиторием. Открывается одной командой, в ней всё: исходники, модели, виды, журнал |
| Маршрут по стадиям | Шаги 01–21 в шести разделах: концепт, чертежи, ракурсы, рендеры, анимация, монтаж | Стадии проекта: ввод, привязка, геометрия, модель, проверка, виды, путь камеры, рендер, видео, выпуск. Статус по каждой |
| Сохранённые виды и запись движения | «Save View», «Tour», «Record», сохранённый облёт идёт дальше как референс | `views.json` (именованные виды) и `paths/` (пути камеры) в проекте. Рендер и видео берут их оттуда, а не из случайных файлов |
| «Ноды» с явными параметрами | Quality, Aspect, Length, Prompt, список референсов | Шаги рендера и видео описываются файлами-рецептами с параметрами, входами и выходами. Повторить шаг значит запустить рецепт |
| Цикл «сделал, сравнил, поправил» | «Before / After», «Move / Rotate», «Vertical fix», «Cut Relief» (убрать рельеф из помещения) | Проверки модели как стадия: коллизии, рельеф под проектом, вертикали. Результат проверки пишется в журнал |
| Библиотека объектов | Созданные модели лежат в Library и переиспользуются | Библиотека проекта и общая библиотека в каталоге: знаки по ГОСТ, малые формы, деревья |
| Навык прикладывается к задаче | Автор прикладывает «видео-скилл» или «скилл для картинок» к чату вместе с материалами | Навыки выбираются под проект и под задачу, фиксируются в проекте и попадают к агенту только выбранные |

## 2. Что не так сейчас

- Рабочая папка плагина совпадает с репозиторием плагина. Данные заказчика лежат в `Обмен\Сириус` и подключаются по абсолютным путям, так что открыть «проект» нельзя, можно только вспомнить пути.
- Скрипты жили во временной папке сессии, в проект их копировали вручную. Потерять их легко.
- Журнала решений нет. Знания остаются в чате: например, то, что страницы PDF повёрнуты на 270° и текст с векторами лежат в другом кадре, чем растр, стоило нам парка, поставленного на проезжую часть. Эту ошибку второй раз сделает любой инженер.
- Версий моделей нет, из `Общий план_v1..v9.ifc` без памяти не понять, чем они отличаются.
- План работ по проекту `docs/PLAN-sirius-model.md` лежит в репозитории плагина, хотя это данные проекта.

## 3. Проект как репозиторий

Инженер подключает папку как проект: `/project-new` в пустой или уже занятой папке выполняет `git init` (без `origin`, сервер поднимем позже) и создаёт каркас.

```
<папка проекта>/            git-репозиторий
  CLAUDE.md                 собирается: инструкции агенту для этого проекта (раздел 5)
  project.json              имя, вид проекта, СК, единицы, стадии и статус, выбранные навыки
  sources/                  исходные чертежи, только чтение; sources.json: файл, хэш, роль, СК, заметки
  work/                     скрипты и промежуточные данные
  models/                   IFC, OBJ, GLB; версии отмечены тегами
  views/                    views.json (виды) и paths/ (пути камеры)
  recipes/                  рецепты рендера и видео
  renders/                  кадры и видео (не в git)
  journal/                  журнал: решения, ошибки, уроки, по датам
  skills-draft/             черновики навыков, родившиеся в этой работе
  .claude/skills/           выбранные навыки, зафиксированные в проекте
  skills.lock.json          какие навыки, какой версии, откуда
```

Правила:
- Проект открыт, значит активен: `project_open` запоминает путь, остальные инструменты (`open_drawing`, `ifc_open` и др.) принимают пути относительно корня проекта и пишут только внутри него. Исходники только читаются.
- Крупные файлы. Кадры и видео не коммитим. Исходные DWG, PDF и IFC пока лежат как есть и описаны в `sources.json` с хэшем, когда появится сервер, включим Git LFS (заготовка `.gitattributes` создаётся сразу).
- Коммиты ставит агент в конце стадии или по запросу, а не на каждое действие. Сообщение коммита собирается из журнала. Задача инженера — ветка `task/<имя>`, по завершении слияние.
- `origin` не настраиваем. Когда сервер появится, достаточно `git remote add`.

## 4. Инструменты и команды

Новый базовый плагин `cad-project`. `dwg-editor` и `3d-editor` берут от него активный проект и корень путей.

| Инструмент MCP | Что делает |
| --- | --- |
| `project_init(path, name, kind, crs, units)` | Каркас, `git init`, первый коммит |
| `project_open(path)`, `project_status()` | Активировать проект, показать стадии, незакоммиченное, выбранные навыки, следующий шаг |
| `source_add(file, role, note)` | Скопировать или записать ссылку на исходник, посчитать хэш, внести в `sources.json` |
| `journal_add(kind, text, refs)` | Запись в журнал: решение, ошибка, урок, проверка |
| `project_commit(message)`, `project_tag(name)` | Коммит, отметка версии модели |
| `skills_catalog(filter)`, `skills_select(names)` | Показать каталог по виду работ и типам чертежей, выбрать и зафиксировать |
| `agent_build()` | Пересобрать `CLAUDE.md` и `.claude/skills/` из выбранного |
| `skill_capture(name, ...)`, `skill_publish()` | Черновик навыка по итогам работы, выгрузка в рабочую копию каталога |

Команды: `/project-new`, `/project-open`, `/project-status`, `/project-skills`, `/skill-capture`, `/skill-publish`.

## 5. Навыки и инструкции агенту

**Файлы для агента собираются отдельно.** Claude Code сам читает `CLAUDE.md` и `.claude/skills/` в папке проекта, поэтому ровно их и собираем: `agent_build` кладёт туда выбранные навыки и общий текст (вид проекта, СК и единицы, правила безопасности, ссылки на журнал и источники). Агент в проекте не видит лишнего, а инженер видит, что именно ему передано.

**Каталог в маркетплейсе** структурируется по двум осям.
- Вид работ: ввод чертежей и привязка, геометрия (оси, профиль, поверхность, покрытия), моделирование, контроль качества, визуализация и видео, документация.
- Тип чертежа: генплан, продольный профиль, поперечные профили, вертикальная планировка, ОДД (знаки и разметка), ведомости, альбом благоустройства.

Формат навыка: `skills/<вид>-<тема>/SKILL.md`, в начале блок со служебными полями поверх обычных `name` и `description`: `kind` (вид работ), `drawings` (типы чертежей), `tools` (какие инструменты MCP нужны), `status` (`draft`, `reviewed`, `stable`), `version`, `origin` (проект и дата). `catalog.json` собирает скрипт из этих полей, он же проверяет формат. Плоские папки нужны, потому что Claude Code ждёт навыки именно так, а структура задаётся полями и каталогом.

**Выбор навыков под задачу.** Установка плагина Claude Code не умеет выбирать отдельные навыки, поэтому выбор двухуровневый.
1. Пакеты в маркетплейсе: `cad-core` (проекты, общие правила, `dwg-editing`), `road-design` (оси, профили, покрытия, ОДД), `landscape` (парк, МАФ, посадки), `bim-ifc` (IFC, коллизии), `visualization` (виды, пролёты, рендер, видео). Ставится только нужное.
2. Выбор для проекта: `/project-skills` показывает каталог, подсвеченный по виду проекта и типам чертежей из `sources.json`, предлагает готовые наборы («Дорога: чертежи → IFC», «Парк», «Пролёт и видео») и записывает выбор в `skills.lock.json` с версиями.

## 6. Как опыт возвращается в каталог

1. В конце задачи агент предлагает `/skill-capture`: из журнала и результата собирается черновик навыка. Обязательные разделы: когда применять, что на входе, шаги, пороги и параметры, ловушки с примерами из проекта, как проверить результат, ссылки на подтверждающие файлы.
2. Черновик остаётся в `skills-draft/` проекта. Данные заказчика (названия, адреса, фамилии) в навык не попадают: перед публикацией идёт проверка по списку.
3. `/skill-publish` копирует черновики в рабочую копию каталога, `skills-incoming/<проект>/`, на ветку `incoming/<проект>-<дата>` и ставит коммит. Отправки нет. Инженер-хранитель каталога смотрит, правит, переводит `draft` в `reviewed`, а затем в `stable`.
4. Уже есть что положить в каталог первыми уроками: привязка листов PDF (кадр векторов и текста против кадра растра), проверка коллизий по вертикальной чётности, дублирование бордюров, вырез рельефа под проектом, пролёт камеры в Blender, браузерный просмотр модели, знаки по ГОСТ Р 52290.

## 9. Решения (приняты заказчиком)

1. **Где живут проекты.** Рекомендую папку вне репозитория плагина и вне Загрузок, например `C:\Projects\<проект>`; один проект — один репозиторий. Путь к «Обмен» остаётся источником, проект копирует исходники или ссылается по хэшу.
2. **Новый плагин `cad-project` или добавить в `dwg-editor`.** Рекомендую новый: `3d-editor` не должен зависеть от DWG-сервера, а проект не должен зависеть от формата чертежей.
3. **Исходники в git.** Рекомендую хранить исходники в проекте и отслеживать через `sources.json` с хэшем сейчас, Git LFS включить вместе с сервером. Альтернатива: всё в git сразу, но репозиторий вырастет на сотни мегабайт.
4. **Именование навыков.** Папки латиницей, описания и тексты по-русски, как сейчас. Поля `kind` и `drawings` фиксированным списком значений.

Принято: проекты в `C:\Projects\<проект>` (вне репозитория плагина и вне Загрузок); новый плагин `cad-project`; репозиторий проекта самодостаточный, потому что станет средой совместной работы инженеров, поэтому исходники лежат в самом репозитории, а не только по хэшу, большие файлы идут через Git LFS (правила заложены сразу, git-lfs на машине есть); папки навыков латиницей, тексты по-русски, поля `kind` и `drawings` фиксированным списком.

## 11. Фотореализм как в гайде

В гайде реалистичность даёт не сцена, а нейросети, которые работают поверх неё. 3D-сцена в 3D Studio грубая и служит носителем геометрии и камеры.
1. Из сцены сохраняются виды 16:9 (`Save View`) и пролёт камеры 8 секунд (`Tour`).
2. Виды обрабатывает нод `Realistic` (картинка в картинку), затем пресеты: `Location` (местность, в примере Новая Зеландия) и `Enhancement` (освещение, выбран пасмурный свет). Результат сравнивают с исходником ползунком «до и после».
3. Видео делают модели `Seedance 2.5` (движение камеры берётся из загруженного видео, внешний вид из картинок, до 30 картинок, 480p, 16:9, ролик 8 или 30 секунд) и `Kling 3` (первая картинка и текстовое описание, 720p, до 15 секунд). Промпт автор пишет в ChatGPT, прикладывая видео, картинки и свой «видео-скилл», который разбирает движение камеры по секундам.
4. Клипы режутся и склеиваются в Video Studio, выпускается один ролик.

Для нашей сцены это значит следующее.
- Улучшать процедурные материалы Blender дальше имеет смысл только ради геометрической точности. Фотореализм берётся другим слоем: наши кадры (чистые, 1920×1080, из сохранённых видов) становятся входом нейросети, а 41-секундный пролёт становится референсом движения. Модель даёт клипы по 8–30 секунд, поэтому ролик собирается из 2–3 клипов (машина, облёт) с монтажом.
- В качестве референсов внешнего вида годятся реальные фото и три видео с телефона по улице Таврическая из папки Сириус.
- Нейросеть может изменить геометрию: положение бордюров, знаки, число деревьев. Для проектной визуализации это нужно помечать «иллюстрация», а точные виды оставлять из нашей сцены. Сверку делать наложением на чистый кадр.
- Загрузка кадров и чертежей во внешний сервис это передача данных заказчика третьей стороне. Это решение заказчика, не наше.
- Что реально делает плагин: подготовка входов (виды, клипы пути камеры, референсы, черновик промпта по навыку) в `renders/ai-input/` и запись параметров в рецепт. Запуск в самом сервисе остаётся за инженером, пока не выяснено, есть ли у сервиса API. В гайде про API ничего нет. Цены и кредиты в гайде не указаны. На локальной видеокарте (GT 1030, 2 ГБ) такие модели не запустить.
